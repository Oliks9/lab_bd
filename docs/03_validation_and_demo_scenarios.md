# Проверка и сценарии демонстрации

Дата актуализации: 27.05.2026

## 1. Цель проверок

Подтвердить, что:

- Oracle-объекты корректно установлены и валидны;
- серверная бизнес-логика работает независимо от GUI;
- ключевые сценарии (авторинг, публикация, прохождение, удаление, администрирование) выполняются без потери консистентности.

## 2. Подготовка окружения

1. Поднять БД и приложение:
   - `powershell -ExecutionPolicy Bypass -File .\docker\start.ps1`
2. При необходимости обновить схему:
   - `powershell -ExecutionPolicy Bypass -File .\docker\upgrade.ps1`
3. Прогнать SQL smoke-тесты:
   - `powershell -ExecutionPolicy Bypass -File .\docker\check.ps1`

## 3. Автоматические SQL-проверки

| Скрипт | Что проверяет | Критерий успеха |
|---|---|---|
| `sql/tests/check_invalid_objects.sql` | Валидность функций, процедур, пакетов, триггеров | Нет `INVALID`, блок завершился без `RAISE` |
| `sql/tests/auth_smoke_test.sql` | Регистрация, вход, создание автора | Возврат корректных ролей `USER`/`AUTHOR` |
| `sql/tests/smoke_test.sql` | Сквозное прохождение демо-теста | Итог `score_percent = 100` |
| `sql/tests/content_management_smoke_test.sql` | Создание/редактирование/публикация/удаление и сбросы | Все контрольные условия выполнены |
| `sql/tests/timezone_smoke_test.sql` | Логика с `TIMESTAMP WITH TIME ZONE` | Попытка остается `IN_PROGRESS` в `+03:00` сессии |

## 4. Матрица ручной проверки ключевой логики

| Сценарий | Шаги | Ожидаемый результат |
|---|---|---|
| Регистрация пользователя | Заполнить форму регистрации и войти | Успешный вход с ролью `USER` |
| Создание автора | Войти под `admin`, создать автора в разделе «Команда» | Новый пользователь получает роль `AUTHOR` |
| Создание тематики/категории | Войти под `AUTHOR`, добавить тему и категорию | Новые записи сразу доступны в UI без повторного входа |
| Создание черновика теста | Автор создает тест и задает `timer_mode`, `attempt_limit`, `show_feedback` | Тест в `DRAFT`, настройки сохранены |
| Редактирование вопроса | Добавить вопрос, затем открыть и изменить поля | Изменения сохранены, старые options заменены при смене типа |
| Публикация теста | Нажать «Опубликовать» | Публикация проходит только при валидной структуре вопросов |
| Возврат в черновик | Для опубликованного теста нажать «Скрыть в черновик» | Статус снова `DRAFT`, доступно редактирование |
| Ограничение попыток | Установить `attempt_limit=1`, пройти тест 2 раза | Вторая попытка блокируется ошибкой лимита |
| Таймер `QUESTION` | Запустить тест с таймером на вопрос, дождаться таймаута | Происходит автопереход к следующему вопросу |
| Показ пояснений | Включать/выключать `show_feedback`, пройти тест | В результате пояснения показываются только при `show_feedback=1` |
| Удаление вопроса | В черновике удалить вопрос | Пересчитаны `seq_no`, статистика попыток и проценты |
| Удаление теста | Удалить тест автора | Тест удален, связанные попытки удалены |
| Сброс по тесту | Под `ADMIN` вызвать сброс попыток пользователя по тесту | У пользователя нет попыток по выбранному тесту |
| Полный сброс | Под `ADMIN` выполнить полный сброс прогресса | У пользователя отсутствуют все попытки |
| Смена пароля | Под `ADMIN` сменить пароль пользователю | Пользователь входит только с новым паролем |
| Удаление пользователя | Под `ADMIN` удалить пользователя не `ADMIN` | Пользователь и его зависимые данные очищены |

## 5. Проверка по PL/SQL API (без GUI)

Рекомендуется демонстрировать преподавателю, что логика живет в БД:

1. `pr_register_user` / `pr_login`.
2. `pkg_admin.create_topic`, `create_category`, `create_quiz`.
3. `pkg_admin.add_question`, `add_option`, `publish_quiz`.
4. `pkg_testing.start_attempt`, `submit_answer`, `finish_attempt`.
5. `pkg_admin.delete_question` / `delete_quiz`.
6. `pkg_admin.reset_user_quiz_attempts` / `reset_user_progress`.

Если вызвать недопустимую операцию, Oracle должен вернуть `RAISE_APPLICATION_ERROR` с соответствующим кодом.

## 7. Критерии «проект работает корректно»

- Все Oracle-объекты имеют статус `VALID`.
- Нет ошибок целостности после удаления вопросов/тестов/пользователей.
- Роли и права соблюдаются на стороне БД.
- Таймеры и оценивание совпадают с бизнес-правилами.
- EXE запускается и успешно подключается к Oracle.
