# Отчет по выполненной работе

Дата актуализации: 22.09.2026

Добавлен подбор N вопросов из категории X сложности Y внутри выбранного теста.
Параметры задаются во вкладке «Подбор» у черновика; отбор, случайный порядок,
проверка достаточного количества и сохранение набора выполняются в Oracle.
Подробности: `07_question_selection.md`.

Реализовано сравнение результата попытки со средним по другим участникам этого теста.
Процедура Oracle `pkg_reports.attempt_result` вычисляет среднее, разницу в процентных
пунктах и размер выборки; GUI показывает текстовую карточку без графиков. Тем самым
реализовано сравнение со средними из пункта 7 исходного задания.

Дополнительно проверено распределение бизнес-логики между Oracle и GUI.
Исправлены серверные проверки таймера, выдачи пояснений, активных попыток и завершения теста;
очистка попыток при входе перенесена в `pr_login`. Кнопки используют текстовые подписи.
Пароль схемы `quiz_app` изменен на `P@ssw0rd`; добавлен скрипт смены без удаления данных.
Подробности и границы реализации описаны в `06_oracle_logic_audit.md`.

## 1. Цель проекта

Разработать полноценную платформу онлайн-квизов, где:

- основная логика выполняется в Oracle (SQL/PLSQL);
- Python выполняет роль GUI-клиента и слоя интеграции;
- критичные правила безопасности и целостности защищены на уровне БД.

## 2. Что реализовано

## 2.1. Архитектура

- Проект структурирован как «боевое» приложение: `app/`, `sql/`, `docs/`, `docker/`, `build/`.
- SQL-слой разделен по типам объектов:
  - `01_tables`, `02_functions`, `03_procedures`, `04_triggers`, `05_packages`, `07_seed`, `08_migrations`, `tests`.
- Python-слой разделен на GUI и БД-доступ:
  - GUI: `app/quiz_client/ui.py`, `app/quiz_client/theme.py`;
  - DB API-обертки: `app/quiz_client/database.py`.

## 2.2. Oracle-слой (итог по объектам)

Реализовано:

- 15 таблиц;
- 5 индексов;
- 4 standalone-функции;
- 2 standalone-процедуры;
- 3 PL/SQL-пакета (`pkg_admin`, `pkg_testing`, `pkg_reports`);
- 5 триггеров;
- 7 процедур отчётности в `pkg_reports`, представления отсутствуют;
- 5 миграций без потери данных;
- 10 SQL smoke-тестов, отдельная проверка seed-данных и 79 Python-тестов в `app/tests`.
- Для закрытых тестов доступен список приглашений и доступа по роли, выдача и отзыв. Проверки выполняет Oracle; результаты, начатые попытки и лимиты сохраняются.
- Установка из GUI: отдельная кнопка выполняет встроенный install.sql после предупреждения и подтверждения имени схемы; есть проверка прав/квоты, фоновый прогресс и журнал. Это переустановка с удалением данных, не обновление.
- Подключение по отдельным полям сервера, порта, SID/Service name с совместимостью старых настроек и без сохранения пароля.
- Автор и администратор меняют доступ черновика между PUBLIC/RESTRICTED; Oracle проверяет права, статус и сохраняет результаты и приглашения.

Подробная техническая карта каждого объекта: `docs/02_database_logic_map.md`.

## 2.3. Пользователи и роли

- Реализованы роли: `USER`, `AUTHOR`, `ADMIN`.
- Реализованы сценарии:
  - регистрация и вход;
  - создание автора администратором;
  - управление ролями;
  - смена пароля пользователя администратором;
  - отключение и повторное включение аккаунта администратором;
  - удаление пользователя администратором с защитными ограничениями.
- Начальные аккаунты новой установки: `admin / Admin123!` (ADMIN), `author / Author123!` (AUTHOR), `student / Student123!` (USER).
- Начальные опубликованные тесты: Oracle, математика и русский язык. Каждый содержит шесть типов вопросов и восемь баллов; два предметных теста принадлежат `author`.
- Seed-данные создаются SQL/PLSQL при установке: 24 завершённых демонстрационных сессии, по 12 у автора и участника, с 144 ответами всех шести типов. Пароли демонстрационные, перед рабочим использованием их нужно сменить.
- Комментарии и описательные docstring убраны из кода проекта; технические объяснения остаются в Markdown-документации.

## 2.4. Контент и публикация тестов

- Автор/админ может управлять:
  - тематиками;
  - категориями;
  - тестами;
  - вопросами и вариантами ответов.
- Поддержаны типы вопросов:
  - `SINGLE_CHOICE`, `MULTIPLE_CHOICE`, `TEXT`, `NUMBER`, `BOOLEAN`, `ORDERING`.
- Реализованы статусы теста:
  - `DRAFT`, `PUBLISHED`, `ARCHIVED` (в проекте архив используется как режим скрытого/чернового теста).
- Реализованы настройки публикации:
  - `show_feedback` (показывать пояснения и правильные ответы в результате);
  - `attempt_limit` (ограничение числа попыток на пользователя);
  - `access_mode` (`PUBLIC`/`RESTRICTED`).

## 2.5. Прохождение теста и оценивание

- Реализованы режимы таймера:
  - `QUIZ` — время на весь тест;
  - `QUESTION` — время на каждый вопрос.
- Реализован серверный автопереход на следующий вопрос при таймауте (`pkg_testing.expire_question`).
- Реализовано серверное оценивание всех типов вопросов.
- Реализован просмотр результатов, включая `given_answer`, `correct_answer`, `explanation` через `pkg_reports.attempt_details`.

## 2.6. Удаление и консистентность

- Удаление вопроса (`pkg_admin.delete_question`):
  - запрещено при активных `IN_PROGRESS` попытках;
  - пересчитывает `seq_no` вопросов;
  - пересчитывает порядок в попытках;
  - пересчитывает баллы и проценты уже существующих попыток.
- Удаление теста (`pkg_admin.delete_quiz`):
  - удаляет попытки по тесту;
  - удаляет сам тест и связанные сущности каскадно.
- Админ-сброс прогресса:
  - по конкретному тесту;
  - полный сброс по пользователю.

## 2.7. Проверки прав и безопасности

- В `pkg_admin` применены guard-процедуры:
  - `require_editor`;
  - `require_admin`;
  - `require_quiz_owner`;
  - `require_quiz_manager`.
- На уровне схемы работают `PK/FK/UNIQUE/CHECK`.
- Триггеры нормализуют данные и пишут аудит-события.
- Все ошибки бизнес-логики возвращаются как `RAISE_APPLICATION_ERROR` с кодами.

## 2.8. Инфраструктура и поставка

- Docker-сценарии:
  - `docker/start.ps1` — старт контейнера и установка;
  - `docker/upgrade.ps1` — обновление схемы;
  - `docker/check.ps1` — прогон SQL smoke-тестов.
- Сборка desktop-приложения:
  - `build/build_exe.ps1`;
  - результат: `dist/OracleQuizPlatform.exe`.

## 3. Что важно для защиты

Для демонстрации «программирования в БД» нужно акцентировать:

- бизнес-правила централизованы в Oracle;
- GUI не содержит критичной логики оценки/прав;
- все операции контента и пользователей проходят через PL/SQL API (`pkg_admin`, `pkg_testing`);
- схема покрыта тестами и валидацией объектов (`VALID`).

## 4. Результат

Получено полноценное приложение с производственной структурой проекта и полной Oracle-ориентированной серверной логикой, готовое для демонстрации, проверки и дальнейшего развития.
